## ArtificialTheorems

The sister repo to [ArtificialAlgorithms](https://github.com/GasStationManager/ArtificialAlgorithms), [ArtificialTheorems](https://github.com/GasStationManager/ArtificialTheorems) is a library of Lean 4 formalizations of theoretical foundations of AI and ML. Formalized results include:
- convergence of stochastic gradient descent, including a formalization of the Robbins-Siegmund theorem from stochastic approximation theory.
- Universal approximation theorem of neural networks.
- Implicit regularization of gradient descent.
- Theory of proper scoring rules.

As mentioned in my [previous post](https://gasstationmanager.github.io/ai/2025/10/23/artificial-alg.html), I am interested in formalizations of foundations of AI/ML, for similar motivations as my interest in [verified code generation](https://gasstationmanager.github.io/ai/2024/11/04/a-proposal.html). In the near future, when our AI writes a paper on AI/ML research, I want to be able to ask it to formalize the theorems in Lean.

I realize that it is wildly optimistic to attempt this as a non-ML-theorist. But look at what's already been formalized in this repo. This is already going beyond my knowledge of ML theory. But it becomes more feasible with the help of Codex and Claude Code.

As usual, comments, suggestions, contributions are appreciated!

## VibeRegistry

If I can do this as a non-expert, imagine what true domain experts can do. Indeed, with the recent release of Anthropic and OpenAI models that are great at Lean, together with coding harnesses like Claude Code and Codex, we are beginning to see more and more autoformalization efforts by mathematicians, physicists, computer science and machine learning theorists.

On the other hand, many of them are relatively new to Lean, and perhaps not all are aware of the potential [pitfalls](https://gasstationmanager.github.io/ai/2024/11/19/progress1.html) of trusting an AI-produced Lean proof once it passed compilation.

In ArtificialTheorems, I have set up a template for robust verification: having a Specs directory containing just the theorem statements, then verifying the proofs against the specs using [SafeVerify](https://github.com/GasStationManager/SafeVerify) and [Comparator](https://github.com/leanprover/comparator). I have scripts that run these locally as well as in GitHub CI. I recommend anyone doing an autoformalization project to adopt a verification framework like this.

Later, I decided to create [VibeRegistry](https://github.com/GasStationManager/VibeRegistry), a registry of external autoformalization repos, that provides:
- safe verification using SafeVerify and Comparator, using the setup outlined above.
- a mechanism for human experts to sign off on the specs.

I added a few entries and plan to add more. Besides pure proofs, I am also interested in vibe-coded software libraries with correctness proofs. Please feel free to send in suggestions as GitHub issues!

With this, I am exploring a decentralized model of building libraries. As the registry expands, I plan to provide functionality to categorize, and to facilitate composition. Without a centrally enforced common set of definitions, this could potentially get messy. But perhaps our AIs will still figure it out.

## Addendum, September 2026: VibeRegistry updates

A few months in, VibeRegistry has changed enough that the description above is out of date.

**Comparator is now the primary check.** It rebuilds the proof in its own sandbox instead of trusting artifacts we produced, and it enforces the statement/proof separation against adversarial Lean. SafeVerify and lean4checker inspect artifacts our own build produced, so for the guarantee we publish they are redundant; both are now opt-in. Also opt-in is [nanoda](https://github.com/ammkrn/nanoda_lib), an independent Lean kernel in Rust — a second kernel is cheap insurance against a bug in the first.

**Some of what I found was in my own pipeline.** Several entries were reporting a pass while nothing was actually being checked: a sandbox flag that quietly swallowed an argument, a theorem filter that treated declaration kinds it didn't recognize as "not a theorem" and dropped them, a version mismatch between the exporter and the checker. A run where the checker returns no verdict now fails instead of reporting green. Each verdict is also bound to a hash of the statement it verified, so editing a spec invalidates the old result rather than inheriting it. One entry now fails honestly, which I prefer to the alternative.

This is the part I keep relearning: the safety of the whole code-with-proof idea is only as strong as the verification pipeline, and a verification pipeline that reports success without checking anything is worse than no pipeline at all, because people believe it.

**Overlay and search.** The registry now mirrors records from [Palomar](https://palomar-registry.org/) and LeanPool — about 1800 statements alongside our own 30. Neither has a human sign-off layer, so ours sits on top of theirs, using the same sign-off interface as our own entries. Everything is browsable and searchable at [gasstationmanager.github.io/VibeRegistry](https://gasstationmanager.github.io/VibeRegistry/), with a sign-off link on each statement.

On the worry I ended with above, about no centrally enforced set of definitions: a small step is that specs are now checked against Mathlib's declaration list, so an entry can't silently shadow a Mathlib name. That catches collisions, not disagreements. The harder problem is still open.
